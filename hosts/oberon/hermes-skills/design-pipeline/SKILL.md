# Design Pipeline

分解が必要な開発依頼を、合意済みの仕様と Hermes kanban タスクへ落とすまでの工程です。
実装は kanban から dispatch される worker プロファイルが行います。この工程では実装しません。

## 開始前

工程に入る前に、次をユーザーへ伝えて承認を得ます。

- これから設計工程 (`grill-with-docs` → `to-spec` → `to-tickets` → `to-kanban`) に入ること
- 対象プロジェクトと board slug (AGENTS.md の「開発依頼の設計」節の表を参照)
- 最初の工程は対話なので、やり取りが数往復続くこと

小さく明確な変更だと分かった場合はこの skill を使わず、AGENTS.md の
「GitHub リポジトリでの作業」に従って直接ブランチを切って PR を出します。

## 工程

必ずこの順番で進めます。工程の省略、順序変更、自動実行は禁止です。
各工程の完了後は、成果物・未解決事項・次に必要な承認を短く報告して**停止**します。

1. `grill-with-docs`
   - 要件、用語、制約、設計判断を対話で確定する
   - 一度に質問する判断は1つだけにする
   - 合意に至るまで次へ進まない
2. `to-spec`
   - 合意内容を実装仕様書へ整理する
   - 作成・更新内容を要約し、ユーザーの明示的な承認を得てから書き出す
3. `to-tickets`
   - 承認済みの仕様書を、実装可能な小さなチケットへ分割する
   - 各チケットに目的、完了条件、依存関係、対象外を含める
   - 出力形式・issue tracker・ラベル語彙は AGENTS.md の「開発依頼の設計」節に従う
4. `to-kanban`
   - チケットファイルを kanban タスクへ変換する
   - assignee は `worker`、workspace は `dir:<リポジトリの絶対パス>`
   - ユーザー承認後にのみ実行する

## ファイル操作

この工程の間、作成・更新してよいのは次の設計成果物だけです。
プロダクトコードには触りません。

- `CONTEXT.md`
- `docs/adr/`
- `docs/specs/`
- `.scratch/<feature-slug>/issues/*.md`

これらを変更する前に、変更内容を要約して明示的な承認を得ます。

## 完了後

kanban へ積んだら、作成したタスクの一覧と board を報告して停止します。
以降の実装の進捗は worker が kanban 上で更新します。
